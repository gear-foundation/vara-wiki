**The Bridge Built-in Actor** enables Gear programs to communicate with Ethereum by sending outbound messages via a standardized interface. It accepts messages of type `Request`, processes them internally, and queues them for relay to the Ethereum network. This actor provides programs with the capability to initiate cross-chain interactions securely and efficiently without requiring additional deployment logic. It is accessible at a fixed address within the Vara runtime.

## Interface

Use the SCALE types from [`gbuiltin-eth-bridge`](https://docs.rs/gbuiltin-eth-bridge/1.10.0/gbuiltin_eth_bridge/), at the version matching the targeted runtime. The request is `Request::SendEthMessage { destination, payload }`. A successful `Response::EthMessageQueued` gives you the original block number, message hash, full `U256` nonce, and queue ID. Keep these values for relay and reconciliation; they confirm enqueueing, not delivery.

<Callout type="warn" title="Transport fee and payload size">
    Ordinary outbound requests must attach at least the current transport fee in Vara base units. The fee is set by governance and read from `gearEthBridge.transportFee`. Any excess attached value is returned on success. Gas and the reply deposit are separate from this value.

    The payload of a single message is limited to **16,384 bytes**.
</Callout>

## Queue a Message from a Vara Program

Call this helper from an async Gear message handler. Pass the actor ID above, the Ethereum destination as `H160`, and the raw application payload. This example uses `gbuiltin-eth-bridge`, `gstd`, and `gprimitives` at `1.10.0`, and `parity-scale-codec` at `3.7.5`.

```rust
extern crate alloc;

use alloc::vec::Vec;
use gbuiltin_eth_bridge::{Request, Response};
use gprimitives::H160;
use gstd::{ActorId, msg};
use parity_scale_codec::{DecodeAll, Encode};

pub async fn queue_message(
    builtin: ActorId,
    destination: H160,
    payload: Vec<u8>,
    transport_fee: u128,
    gas_limit: u64,
    reply_deposit: u64,
) -> Result<Response, &'static str> {
    let request = Request::SendEthMessage { destination, payload }.encode();
    let pending = msg::send_bytes_with_gas_for_reply(
        builtin,
        request,
        gas_limit,
        transport_fee,
        reply_deposit,
    )
    .map_err(|_| "could not start bridge request")?;
    let bytes = pending.await.map_err(|_| "bridge reply failed")?;
    Response::decode_all(&mut bytes.as_slice()).map_err(|_| "invalid bridge reply")
}
```

Reconcile the original request against finalized Vara history before retrying an uncertain outcome. Setting up the reply can fail after the message has been sent, and a missing or undecodable reply does not prove that nothing was queued.

Queued messages are delivered to Ethereum by the [Vara ↔ Ethereum Bridge](/docs/vara-network/bridge/bridge_technical): Vara validators commit to the message queue through BEEFY, and the `MessageQueue` contract on Ethereum processes each message after verifying it against that commitment.

For the complete queue-to-delivery flow, see the [Vara → Ethereum App Guide](/docs/vara-network/bridge/developer-guide-vara-eth).
