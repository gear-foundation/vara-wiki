# Reverse Gas Model

In traditional blockchains, users pay gas for every transaction. Vara.eth flips this: **programs pay for their own execution**, and users only pay standard Ethereum gas for the L1 transaction.

## How It Works

When a user submits a message through an Ethereum Mirror contract, the wallet pays ETH for the L1 transaction. Its fee depends on gas used and the effective gas price. A developer, user, or sponsor can fund the program’s Executable Balance so that the sender does not need wVARA to pay for computation.

## Execution Pricing

For ordinary message execution, the runtime meters gas burned, converts it to wVARA base units, and deducts the charge from the program’s Executable Balance. More work can consume more of that balance even when the message ends in an error.

One narrow exception applies when an injected message panics on its first execution and burns at most the runtime’s panic-charge threshold. In that case the runtime skips the executable-balance charge. Successful messages pay for the gas they burn, including small calls. ## Executable Balance Management

### Funding

Follow [Funding Executable Balance](/docs/vara-eth/interact/funding-executable-balance) to select the Router's wVARA, convert it to base units, and top up the Mirror.

### Monitoring

```typescript
// Read state and take executableBalance field
const mirror = getMirrorClient(programId, signer, publicClient);
const stateHash = await mirror.stateHash();
const state = await api.query.program.readState(stateHash);
console.log(`Executable balance: ${state.executableBalance} base units`);
```

### What Happens When Balance Runs Out

A message can return an out-of-gas error when its program is underfunded. A top-up adds execution capacity. Check the original reply before retrying. See [What Happens When Balance Runs Out](/docs/vara-eth/interact/funding-executable-balance#what-happens-when-balance-runs-out).

## Cost Optimization

- **Minimize computation in hot paths** — avoid unnecessary work in frequently called methods
- **Use lazy evaluation** — don't compute what isn't needed
- **Batch operations** in single messages when possible
- **Cache computed values** in state rather than recomputing
- **Keep payloads small** — less data to decode
- **Monitor consumption patterns** and right-size funding with automated alerts
