---
title: Ethereum → Vara App Guide
---

This guide follows one application ping from Ethereum to Vara. The Vara light client authenticates Ethereum finality; the receipt proof authenticates the execution log. Your receiving program decides which emitter, event, and payload it accepts. To send a reply back, follow the [Vara → Ethereum App Guide](/docs/vara-network/bridge/developer-guide-vara-eth).

## High-Level Architecture

1. An Ethereum application contract emits the ping event in a successful transaction.
2. A relayer builds a proof of the receipt against finalized Ethereum history supported by the checkpoint light client on Vara.
3. The Historical Proxy routes the proof to the verifier configured for the Ethereum slot. After verification, it forwards the authenticated receipt to the Vara application.

Use the deployment identities from the [Developer Hub](/docs/vara-network/bridge/developer_hub). The example covers application code; proof tooling must support the selected checkpoint, verifier, and receiver interface. A proxy acknowledgement is not proof of application success.

## Emit and Identify the Ping on Ethereum

This example emits `MessageRequested`, an application event, not a bridge-wide event ABI. Deploy it with the authorized Ethereum sender and the full 32-byte ID of your Vara program. Configure the Vara receiver to expect this emitter address, sender, and event ABI.

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.28;

contract EthereumPingSender {
    address public immutable sender;
    bytes32 public immutable destination;

    event MessageRequested(
        bytes32 indexed applicationId,
        address indexed sender,
        bytes32 indexed destination,
        bytes payload
    );

    constructor(address authorizedSender, bytes32 varaDestination) {
        require(authorizedSender != address(0) && varaDestination != bytes32(0), "invalid configuration");
        sender = authorizedSender;
        destination = varaDestination;
    }

    function sendMessage(bytes32 applicationId, bytes calldata payload) external {
        require(msg.sender == sender, "wrong sender");
        require(applicationId != bytes32(0) && payload.length <= 1024, "invalid ping");
        emit MessageRequested(applicationId, msg.sender, destination, payload);
    }
}
```

The 1,024-byte limit belongs to the ping application, not the receipt bridge. Use a unique application ID, and record the Ethereum chain, emitter address, transaction hash, and expected event. A transaction hash identifies the receipt, not an individual log.

## Relay the Original Receipt

1. Wait for Ethereum finality and for the matching checkpoint evidence to be accepted on Vara. An Ethereum transaction being mined does not meet either condition.
2. Build the execution receipt trie proof and the Beacon proof that binds it to authenticated Ethereum history. Send it to the configured Historical Proxy using the verifier and consumer interface for that slot.
3. Track the original Vara transaction and the receiver's finalized reply. If the result is unknown, reconcile the original submission rather than resending the source ping.

## Authenticate the Ping on Vara

Configure the relayer to forward to your receiver's Sails service and method, for example `Ping` and `SubmitReceipt`. After the slot-specific verifier accepts the proof, the Historical Proxy prefixes the receiver's route to the SCALE-encoded arguments below. The service name, method name, and return type are application-defined.

```text
(slot: u64, transaction_index: u64, receipt_rlp: vec u8)
```

Match the receipt encoding used by the configured verifier; do not assume all deployments forward the same RLP framing. Before applying the ping:

1. Require the runtime message source to be the configured Historical Proxy actor. Calling an exported handler directly must not authenticate a receipt.
2. Decode the receipt, require a successful Ethereum transaction, and match the configured emitter and `MessageRequested` signature. Validate the decoded ABI, the authorized Ethereum sender, this program's actor ID as `destination`, the nonzero application ID, and the payload. Reject a receipt without exactly one matching event.
3. Reject replay using the verified receipt position (slot and transaction index) and the accepted application ID. If the handler supports several events per receipt, include the receipt-local log position when tracking consumption.
4. Record the accepted ID and payload as the application effect and return an explicit success result.

## Verification

Check that the original submission finalized on Vara and that the receiver stored the expected ping ID and payload. A finalized checkpoint makes proof verification possible; it is not delivery. Test that direct calls, wrong emitters or event signatures, malformed payloads, and duplicate pings do not change receiver state.
