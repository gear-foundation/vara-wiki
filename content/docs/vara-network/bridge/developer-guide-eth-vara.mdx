---
title: Ethereum → Vara App Guide
---

This guide follows one application ping from Ethereum to Vara. The Vara light client authenticates Ethereum finality; the receipt proof authenticates the execution log. Your receiving program decides which emitter, event, and payload it accepts. To send a reply back, follow the [Vara → Ethereum App Guide](/docs/vara-network/bridge/developer-guide-vara-eth).

## High-Level Architecture

1. An Ethereum application contract emits the ping event in a successful transaction.
2. A relayer builds a proof of the receipt against finalized Ethereum history supported by the checkpoint light client on Vara.
3. The Historical Proxy routes the proof to the verifier configured for the Ethereum slot. After verification, it forwards the authenticated receipt to the Vara application.

Use the configured deployment identities from the [Developer Hub](/docs/vara-network/bridge/developer_hub). This guide describes the protocol and application checks, not an SDK quickstart. Pin your proof tooling to a version that supports the selected checkpoint, verifier, and receiver interface. Do not use a generic acknowledgement from the proxy as evidence of application success.

## Emit and Identify the Ping on Ethereum

Give the event a stable ABI, for example `PingFromEthereum(bytes32 indexed pingId, bytes payload)`. Use an application ID that uniquely identifies the action. Record the Ethereum chain, emitter address, transaction hash, and the expected event. If one receipt can contain several matching logs, define how each is identified and processed; a transaction hash alone does not select an event.

## Relay the Original Receipt

1. Wait for Ethereum finality and for the matching checkpoint evidence to be accepted on Vara. An Ethereum transaction being mined does not meet either condition.
2. Build the execution receipt trie proof and the Beacon proof that binds it to authenticated Ethereum history. Send it to the configured Historical Proxy using the verifier and consumer interface for that slot.
3. Track the original Vara transaction and the receiver's finalized reply. If the result is unknown, reconcile the original submission rather than resending the source ping.

## Authenticate the Ping on Vara

Expose a receipt handler such as `SubmitReceipt`, using the argument types and receipt encoding required by the deployed verifier. Before applying the ping:

1. Require the runtime message source to be the configured Historical Proxy actor. Calling an exported handler directly must not authenticate a receipt.
2. Decode the authenticated receipt and require the expected Ethereum emitter address, event signature topic, and event ABI. Validate the full application payload. For a single-ping handler, reject a receipt without exactly one matching event.
3. Reject replay using the verified receipt position (slot and transaction index) and the accepted application ID. If the handler supports several events per receipt, include the receipt-local log position when tracking consumption.
4. Record the accepted ID and payload as the application effect and return an explicit success result.

## Verification

Check that the original submission finalized on Vara and that the receiver stored the expected ping ID and payload. A finalized checkpoint makes proof verification possible; it is not delivery. Test that direct calls, wrong emitters or event signatures, malformed payloads, and duplicate pings do not change receiver state.
