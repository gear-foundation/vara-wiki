---
title: Vara → Ethereum App Guide
---

This guide follows a one-way application ping from Vara to Ethereum. `BeefyClient` authenticates Vara finality. `MessageQueue` verifies the ping's inclusion in a registered queue root and dispatches it. Your application still decides which source actor and payload it accepts. The [Ethereum → Vara App Guide](/docs/vara-network/bridge/developer-guide-eth-vara) uses a separate example; the two are not a ping/pong pair.

## High-Level Architecture

1. A Vara program queues a ping addressed to its Ethereum receiver.
2. A relayer submits an inclusion proof for the original message after the selected queue root has matured.
3. The Ethereum receiver authenticates the caller and source actor, then records the ping.

Use the deployment identities from the [Developer Hub](/docs/vara-network/bridge/developer_hub). Publishing a Vara queue root to Ethereum is separate from proving and executing an application message. These steps start with an already registered root; they do not publish a BEEFY commitment.

## Queue a Ping on Vara

- Configure the Ethereum receiver address in your Vara program. For the receiver below, use the [built-in actor example](/docs/developing/build/builtinactors/bia-bridge#queue-a-message-from-a-vara-program) with the raw 32 bytes of a unique, nonzero ping ID as `payload`. A single ABI-encoded `bytes32` is exactly those bytes; do not SCALE-encode the ID as a vector inside `payload`.
- Read the current `gearEthBridge.transportFee` in Vara base units. Pass it to the program and attach that value to the `SendEthMessage` request to the [Bridge Built-in Actor](/docs/developing/build/builtinactors/bia-bridge), separately from message gas and the reply deposit. Handle fee changes and insufficient-value errors instead of hardcoding a zero fee.
- After a successful queue reply, retain the original Vara block, message hash, and **full `U256` nonce**. In JavaScript, use `bigint`, not `number`. A queue reply confirms enqueueing, not delivery.

## Relay the Original Message

1. Find the message in finalized Vara history. Select a registered queue snapshot that includes it. Use an archive Vara endpoint and [`@gear-js/api`](https://www.npmjs.com/package/@gear-js/api) to call `api.ethBridge.merkleProof(messageHash, snapshotBlockHash)`, using the selected snapshot's Vara block hash, not necessarily the block that enqueued the ping. Use the original message hash from the queue reply and compare the returned `root` to `MessageQueue.getMerkleRoot(snapshotBlockNumber)`.
2. Confirm that the root for the **selected Vara block number** has matured on Ethereum. For a user message, read `PROCESS_USER_MESSAGE_DELAY` (currently 300 seconds) and `getMerkleRootTimestampForBlock(snapshotBlockNumber)`. Do not infer maturity from the same root hash registered at a different block.
3. With [viem](https://viem.sh/docs/contract/simulateContract), simulate `MessageQueue.processMessage(snapshotBlockNumber, number_of_leaves, leaf_index, message, proof)` against the configured proxy before sending the transaction. Pass the original `(nonce, source, destination, payload)` as `message`; take `number_of_leaves`, `leaf_index`, and `proof` from the Vara RPC result. If submission is pending or its outcome is unknown, reconcile the original transaction before retrying. Do not send a new ping to replace an unresolved one.

The published [`@gear-js/bridge@0.2.0`](https://www.npmjs.com/package/@gear-js/bridge/v/0.2.0) exports `relayVaraToEth`, but it uses legacy GRANDPA authority-set checks when selecting a later root, and its `wait` option waits for registration, not maturity. Use the explicit snapshot steps above for BEEFY-backed roots.

## Authenticate the Ping on Ethereum

The queue calls `handleMessage(bytes32 source, bytes calldata payload)` on the destination contract. Set `messageQueue` to the configured **proxy** address and `varaSource` to the full 32-byte actor ID of your Vara program.

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.28;

contract VaraPingReceiver {
    address public immutable messageQueue;
    bytes32 public immutable varaSource;
    mapping(bytes32 => bool) public received;

    event PingReceived(bytes32 indexed pingId);

    constructor(address queue, bytes32 source) {
        require(queue != address(0) && source != bytes32(0), "invalid configuration");
        messageQueue = queue;
        varaSource = source;
    }

    function handleMessage(bytes32 source, bytes calldata payload) external {
        require(msg.sender == messageQueue, "not the queue");
        require(source == varaSource, "wrong Vara source");
        require(payload.length == 32, "invalid payload length");

        bytes32 pingId = abi.decode(payload, (bytes32));
        require(pingId != bytes32(0) && !received[pingId], "invalid or repeated ping");
        received[pingId] = true;
        emit PingReceived(pingId);
    }
}
```

The queue prevents replay of a bridge nonce. An application-level ID also prevents applying the same logical action twice if the source sends it under two different nonces.

## End-to-End Verification

Check the original successful, finalized Ethereum transaction. Match the queue's `MessageProcessed` event to the original message and the receiver's event or state to the expected `pingId`. Root publication or a processed nonce alone does not prove the intended application effect. Test that direct calls, messages from another Vara actor, and duplicate application IDs do not change receiver state.
